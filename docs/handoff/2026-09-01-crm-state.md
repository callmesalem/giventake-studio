## 3. Database — applied, but the history does not match the repo

All objects from both migrations exist and were verified by query:
`channel_auth_log`, `channel_auth_too_many_failures`, `campaign_claim_step`,
`campaign_mark_by_message`. `leads_list` returns `owner_id` and `assigned_to`.

**The version numbers do not line up.** They were applied through the Supabase
MCP tool, which assigns its own timestamp:

| Repo file | Recorded in the DB as |
|---|---|
| `20260831120000_campaign_engine.sql` | `20260831215131` |
| `20260831140000_channel_auth.sql` | `20260831233011` |
| `20260830210000_leads_list_owner_fields.sql` | not recorded at all (effect is present) |

Nothing automated runs `supabase db push` — CI does not migrate and no script
calls it — so this is bookkeeping-only **today**. It becomes real the first time
anyone pushes: the CLI would see three local versions missing from remote
history and re-run them. All three are idempotent (`create table if not exists`,
`create index if not exists`, `add column if not exists`, `create or replace
function`, no enums, no policies, no top-level inserts, no drops), so a re-run
should be harmless — but "should be" is doing work in that sentence, and the
`create or replace function` statements would silently overwrite any later
hand-edit to those functions.

Fix when someone wants to: record the three repo versions as applied and drop
the two MCP-assigned rows, so history matches the tree.

## 4. The campaign engine is armed but inert — on purpose

The five-minute cron **is** firing in production. It does nothing, and cannot,
until three values are set:

- `CAMPAIGN_TOKEN_SECRET` — a dashboard Secret. The runner refuses to claim any
  row without it, and the unsubscribe verifier rejects an empty secret outright
  (an empty HMAC key is public knowledge, so every token would be forgeable).
- `CAMPAIGN_REPLY_TO` — must be a mailbox Cloudflare Email Routing actually
  delivers to this Worker, or replies stop being detected and the sequence keeps
  mailing someone who already answered. Deliberately not guessed.
- `CAMPAIGN_UNSUBSCRIBE_BASE` — e.g. `https://giventakedevs.com/api/unsubscribe`.

The last two are plain values and belong in `wrangler.jsonc`, **not** only in the
dashboard: plain vars are part of the uploaded config, so a deploy replaces them
with whatever the file says. That is not hypothetical — it dropped
`INTAKE_FROM_EMAIL` on 2026-08-21 and silently reverted the contact form to its
`mailto:` fallback.

Verified inert: `campaign_sends`, `campaign_events` and `campaign_enrollments`
are all empty.

Targeting stays human. `approved_recipients` is a positive, per-SOP allowlist
with no agent-callable insert RPC; the engine automates timing only.

## 8. Environment trap: the repo is inside OneDrive

**The working tree AND `.git` are inside a OneDrive Files-On-Demand sync root.**
The Desktop is OneDrive-backed and the repo sits on it. Measured, not assumed:
every directory — `src`, `tests`, `node_modules` and `.git/objects` — carries the
`ReparsePoint` attribute with an empty `LinkType` and empty `Target`, which is
the OneDrive cloud-placeholder tag rather than a junction.

### The symptom it produces

`src/routeTree.gen.ts` intermittently shows as modified when it is byte-identical
to HEAD, and that blocks `git checkout <branch>`:

```
error: Your local changes to the following files would be overwritten by checkout:
        src/routeTree.gen.ts
```

What makes it confusing is that every content check says the file is clean —
same size (32530), same `git hash-object` sha as the index entry, empty
`git diff`, empty `git diff HEAD`, empty `git diff --raw`, zero CR bytes — while
`git update-index --really-refresh` still reports `needs update`. That
combination is a **stat-level** disagreement, not a content one.

It is non-deterministic. The same test loop triggered it three times one session
and ran clean twice the next, which is what makes it so easy to blame on whatever
command happened to run just before.

### Do not blame the tests, or line endings

Both were investigated and both are innocent:

- **No test writes it.** Nothing under `tests/` writes any file, and
  `vitest.config.ts` does not carry the TanStack plugin, so the component suite
  does not regenerate it either. The route tree is regenerated by `vite build`.
- **Line endings are a separate, real, already-fixed problem.** `.gitattributes`
  pinned the tree to LF and killed the ~21,000 phantom `Delete CR` prettier
  errors. It was never going to fix the checkout blocking, because that has a
  different cause. One symptom, two faults — fixing the first and assuming the
  second went with it is exactly the mistake to avoid here.

### Mitigation applied (repo-local, reversible)

```
git config --local core.trustctime false    # OneDrive rewrites ctime constantly
git config --local core.checkStat  minimal  # compare size + whole-second mtime only
```

Git's defaults compare ctime, inode, uid/gid and dev, every one of which is
unstable on this filesystem. `core.fscache` is left at Windows' default `true`.

These are **local config, not committed** — a fresh clone will not have them, so
re-apply them after cloning. And because the fault cannot be reproduced on
demand, this is a mitigation whose effectiveness is unproven, not a verified fix.

**If it recurs:** `git checkout -- src/routeTree.gen.ts`, then switch branches.
The file is identical to HEAD, so nothing is lost.

### The part config cannot fix

Phantom modifications are the mild symptom. The real hazard is that
**`.git/objects` is being synced by OneDrive.** A cloud sync client writing into
a git object store can corrupt the repository, and no git setting prevents that.
The same session that found this also hit `Permission denied` deleting
`.git/worktrees/wt`, which is OneDrive holding handles inside `.git`.

The actual fix is to move the repo out of the sync root — e.g. `C:\dev\` — or
exclude the folder in OneDrive settings. Until then, treat any inexplicable git
behaviour here as environmental first and a bug second.
